# MBN Health — ملف شامل حول المشروع
### إعداد للعرض على المستشار الاستراتيجي — تقييم الجاهزية قبل التوسّع

**تاريخ الإعداد:** 4 يوليو 2026
**الغرض من الملف:** تزويد المستشار الاستراتيجي بصورة كاملة ودقيقة عن حالة المشروع الحالية (ما تم بناؤه فعليًا، بعمق حقيقي وليس عرضًا تسويقيًا)، تمهيدًا لمناقشة القرارات التالية: هل المشروع جاهز للتوسّع؟ ما الفجوات التي يجب سدّها أولًا؟ وهل هناك حاجة لموارد إضافية (فريق، تمويل، شراكات) قبل أي خطوة توسعية جديدة؟

---

## 1. لمحة عامة عن المشروع

**MBN Health** هو منصة SaaS متعددة المستأجرين (Multi-Tenant) لإدارة العيادات الطبية، مبنية لتخدم عيادات حقيقية — وليست نسخة تجريبية أو Prototype تسويقي. المشروع عبارة عن Monorepo يضم:

- **واجهة خلفية (API):** مبنية بـ NestJS
- **واجهة أمامية (لوحة تحكم):** مبنية بـ Next.js 14
- **طبقة بيانات مشتركة:** PostgreSQL عبر Prisma ORM

الفكرة الأساسية: عيادة تشترك في المنصة، تحصل على نطاق خاص بها (Tenant)، وتدير من خلاله كل شيء — المرضى، المواعيد، السجلات الطبية، الفوترة، المخزون، وحتى التواصل مع مرضاها عبر واتساب — مع عزل تام لبيانات كل عيادة عن الأخرى.

### الفئة المستهدفة (Target Market)
عيادات ومراكز طبية صغيرة إلى متوسطة الحجم تحتاج نظامًا متكاملًا (EHR + Scheduling + Billing + Communication) بدل استخدام أدوات متفرقة (واتساب يدوي، إكسل للفوترة، دفتر مواعيد ورقي).

## 2. النموذج التجاري (Business Model)

نموذج **اشتراك شهري متدرّج (Subscription SaaS)** مبني على Stripe Checkout + Billing Portal، مع 3 مستويات تسعير معرّفة في النظام:

| الخطة | الحالة الحالية |
|---|---|
| Starter | معرّفة في النظام، تحتاج ربط بمعرّف سعر حقيقي في Stripe |
| Professional | معرّفة في النظام (هي خطة العيادة التجريبية المزروعة في قاعدة البيانات — 25 مقعدًا) |
| Enterprise | معرّفة في النظام، تحتاج ربط بمعرّف سعر حقيقي في Stripe |

**ملاحظة مهمة للمستشار:** آلية الفوترة (Checkout، Billing Portal، Webhooks) **مبنية وتعمل تقنيًا**، لكن **لا توجد بعد استراتيجية تسعير فعلية** (ما هي الأسعار؟ ما الفرق الوظيفي بين الخطط الثلاث من حيث الحدود — عدد المستخدمين، عدد المرضى، الميزات المتاحة؟). هذه نقطة أولى يجب حسمها قبل أي إطلاق تجاري أو توسّع.

## 3. البنية التقنية (Technology Stack)

| الطبقة | التقنية |
|---|---|
| الواجهة الأمامية | Next.js 14 (App Router)، React 18، TypeScript، Tailwind CSS، Radix UI، Framer Motion، TanStack Query/Table، React Hook Form + Zod |
| الواجهة الخلفية | NestJS، TypeScript، REST API، Passport/JWT، class-validator |
| قاعدة البيانات | PostgreSQL + Prisma ORM (36 نموذج بيانات/جدول رئيسي) |
| المصادقة | JWT (Access + Refresh دوّار)، مصادقة ثنائية TOTP، صلاحيات قائمة على الأدوار (RBAC)، إدارة جلسات |
| المراسلة | تكامل حقيقي مع WhatsApp Business Cloud API (Meta) + مساعد ذكاء اصطناعي محدود الصلاحيات (Claude) |
| المهام المجدولة | Vercel Cron (تذكيرات المواعيد يوميًا) — لا يوجد طابور خلفي (Queue) بتصميم متعمّد |
| الفوترة/الاشتراكات | Stripe Checkout + Billing Portal + Webhooks |
| التخزين | تخزين كائنات متوافق مع S3 (MinIO محليًا) |
| النشر | مشروع Vercel واحد للواجهتين، مع بدائل Docker Compose وKubernetes للاستضافة الذاتية |

**قرار معماري مهم:** النظام مصمم ليعمل بالكامل على بنية Serverless (Vercel) بدون عمليات خلفية دائمة (لا Redis، لا BullMQ). هذا قرار مقصود يبسّط التشغيل ويقلل التكلفة، لكنه **يفرض قيدًا حقيقيًا**: خطة Vercel المجانية/الأساسية (Hobby) تسمح بتشغيل المهام المجدولة **مرة واحدة يوميًا فقط** — أي أن تذكيرات المواعيد عبر واتساب تُرسل مرة واحدة يوميًا (الساعة 8 صباحًا UTC) وليس بشكل لحظي. الترقية لخطة Vercel Pro تحل هذا القيد وتتيح تكرارًا أعلى (كل ساعة مثلاً).

## 4. الوحدات الوظيفية — أين العمق الحقيقي وأين البساطة

المشروع مبني بمبدأ "عمق حقيقي في الوحدات الأساسية، ووظائف بسيطة لكن حقيقية (وليست شكلية) في البقية". كل وحدة، عميقة كانت أو بسيطة، لديها: مخطط بيانات حقيقي في Prisma، نقاط REST API حقيقية مع تطبيق صلاحيات وعزل بيانات لكل عيادة، وواجهة مستخدم متصلة ببيانات حقيقية (وليست بيانات وهمية/Mock).

### وحدات بعمق إنتاجي كامل (Deep)
- **المصادقة وتعدد المستأجرين (Auth & Multi-Tenancy)**
- **لوحة التحكم والتحليلات (Dashboard/Analytics)**
- **المرضى والسجل الطبي الإلكتروني (Patients & EHR)**
- **المواعيد** (تقويم يومي/أسبوعي/شهري، سحب-وإفلات لإعادة الجدولة، سير حالة كامل، قائمة انتظار)
- **الأطباء والأقسام**
- **السجلات الطبية (ملاحظات SOAP)**
- **الوصفات الطبية**
- **الفوترة** (فواتير، مدفوعات، مطالبات تأمين)
- **تكامل واتساب** (Webhook حقيقي مع Meta Cloud API، إرسال، تذكيرات مجدولة، مساعد ذكاء اصطناعي محدود)
- **فوترة اشتراك Stripe** (Checkout، Billing Portal، Webhooks)

### وحدات وظيفية بسيطة لكنها حقيقية (Thin)
المختبر (Laboratory)، الأشعة (Radiology)، المخزون (Inventory)، الدردشة الداخلية للموظفين، قوالب الرسائل، التقارير وتصدير CSV، إدارة الموظفين، سجلات التدقيق (Audit Logs).

### غير منفَّذ بعد (موثّق بصراحة، وليس مموّهًا)
- إشعارات Push حقيقية (Push Notification Delivery)
- التوقيع الإلكتروني على نماذج الموافقة (Consent Forms)
- توليد الشهادات الطبية
- ميزات ذكاء اصطناعي إضافية (تلخيص الملاحظات الطبية آليًا، جدولة محسّنة بالذكاء الاصطناعي)

**هذا التمييز الصريح بين "عميق/بسيط/غير منفَّذ" هو نقطة قوة نادرة في عرض المشاريع — يعطي المستشار صورة واقعية بدل وعود تسويقية.**

## 5. تكامل واتساب والمساعد الذكي — تفصيل خاص لأنه الميزة التفاضلية

تم **إلغاء دعم الرسائل النصية (SMS) بالكامل** كقرار منتج، لصالح تكامل واتساب حقيقي بالكامل:

- **بروتوكول حقيقي وليس محاكاة:** التحقق من توقيع Meta (X-Hub-Signature-256)، مصافحة رمز التحقق، وإرسال فعلي عبر graph.facebook.com. في حال عدم ضبط رقم هاتف لعيادة معينة، يتم تسجيل الإرسال كـ"محاكاة" (SIMULATED) بدل الفشل الصامت.
- **معمارية بدون عمليات خلفية:** الرسائل الواردة تُعالَج بشكل متزامن ضمن معالج Webhook نفسه، مع حماية من إعادة إرسال Meta عبر فحص تكرار المعرف.
- **المساعد الذكي محدود عمدًا:** يستطيع فقط (1) الإجابة عن أسئلة عامة عن العيادة (أوقات الدوام، العنوان، الهاتف) و(2) الاستعلام عن مواعيد المريض المطابق لرقمه فقط — قراءة فقط، ولا يمكنه الحجز أو الإلغاء أو تقديم استشارة طبية. أي طلب خارج نطاقه يُحال لموظف بشري.
- بدون مفتاح Anthropic API، يتحول النظام تلقائيًا لرسالة "سيتواصل معك أحد الموظفين" بدل حدوث خطأ.

**هذه الميزة تم التحقق منها فعليًا (End-to-End) في بيئة تطوير حقيقية**، وليست مجرد كود غير مُختبر.

## 6. الأمان والامتثال

### ما هو مطبَّق فعليًا
- كلمات المرور مشفّرة بخوارزمية Argon2id؛ رموز التحديث (Refresh Tokens) مخزّنة كـ Hash بـ SHA-256 وتُجدَّد مع كل استخدام
- صلاحيات قائمة على الأدوار (RBAC) عبر PermissionsGuard، مع عزل كل استعلام حسب tenantId مأخوذ من رمز JWT الموثّق فقط (لا يمكن لعيادة الوصول لبيانات عيادة أخرى بتخمين معرّف)
- مصادقة ثنائية (TOTP) مع رموز استرداد، Helmet، وحدّ معدل طلبات (Rate Limiter) عام مع حدّ أشد صرامة على تسجيل الدخول
- التحقق من توقيعات Webhook (واتساب وStripe) قبل الوثوق بأي حمولة بيانات
- رمز وصول واتساب لا يُعاد للواجهة الأمامية أبدًا — فقط معاينة مقنّعة
- كل الإجراءات الحساسة (تسجيل دخول، فشل الدخول، إنشاء/تعديل/حذف) تُسجَّل في سجل تدقيق (AuditLog) مع الفاعل وعنوان IP ومعلومات المتصفح

### ما هو **غير** مكتمل بعد — نقطة حرجة للمستشار
النظام نفسه يوثّق بصراحة أن هذا **"أساس متين وليس برنامج امتثال مكتمل"**. قبل أي إطلاق حقيقي أو توسّع تسويقي، يلزم:
1. مراجعة أمنية من طرف ثالث (Third-Party Security Audit)
2. تفعيل تشفير البيانات أثناء التخزين (Encryption at Rest) على مزوّد Postgres/S3 المختار
3. سياسة مكتوبة للاستجابة للحوادث والنسخ الاحتياطي (Incident Response & Backup Policy)
4. إدارة أسرار (Secrets Manager) حقيقية أمام مفاتيح واتساب وStripe (حاليًا في متغيرات بيئة عادية أو عمود قاعدة بيانات)
5. **لا يمكن اعتبار النظام جاهزًا لمعايير GDPR/HIPAA قبل إنجاز ما سبق** — وهذا أمر بالغ الأهمية إذا كان التوسّع يشمل أسواقًا أو عملاء يشترطون هذه المعايير (تأمين صحي، مستشفيات، عملاء أوروبيون/أمريكيون).

## 7. الجودة والاختبار

جميع مجموعات الاختبار التالية **تعمل فعليًا ضد بنية تحتية حقيقية** (وليست اختبارات وهمية):

| نوع الاختبار | العدد | التغطية |
|---|---|---|
| اختبارات وحدة (API) | 18 | المصادقة/RBAC، تعارض المواعيد وسير الحالة، حسابات الفواتير/المدفوعات، منطق إرسال واتساب، تدرّج المساعد الذكي |
| اختبارات شاملة (API e2e) | 5 | إقلاع كامل للتطبيق ضد قاعدة بيانات حقيقية، تدفق المصادقة، تطبيق RBAC |
| اختبارات متصفح (Playwright) | 19 | تسجيل الدخول، كل مسار تنقل رئيسي، تسجيل مريض كامل، تبديل عرض التقويم، شاشة إعدادات واتساب |

يعمل خط CI (GitHub Actions) على تشغيل الحزم الثلاث تلقائيًا. **بناء Docker لم يُختبر فعليًا بتشغيل حقيقي** (تم التحقق منه بناءً على أنماط موثّقة فقط) — يحتاج تحقق فعلي على جهاز يحتوي Docker قبل الاعتماد عليه في الإنتاج.

## 8. النشر والبنية التحتية

**الهدف الأساسي:** Vercel، مشروع واحد للواجهتين (الأمامية كتطبيق Next.js عادي، والخلفية كدالة Serverless عبر إعداد NestJS الجاهز في Vercel).

**قيود يجب معرفتها:**
- قاعدة بيانات يجب أن تكون Pooled (مثل Neon أو Supabase أو PgBouncer) — لأن الدوال Serverless تفتح اتصالًا جديدًا بقاعدة البيانات مع كل Cold Start، وقاعدة بيانات غير مجمّعة (Unpooled) ستنفد اتصالاتها تحت حمل حقيقي.
- لا يوجد طابور رسائل (Queue) ولا Cron داخل العملية — بتصميم متعمد يناسب Serverless لكنه يحد من إمكانية التوسّع لعمليات ثقيلة مستقبلية (مثل إرسال آلاف التذكيرات دفعة واحدة).

**بديل الاستضافة الذاتية:** متوفر بالكامل عبر docker-compose.yml وK8s manifests (Deployment/Service/HPA/Ingress مع TLS)، لمن يفضل عدم الاعتماد على Vercel.

## 9. نقاط القوة (لعرضها على المستشار)

1. **صدق تقني نادر:** التوثيق الداخلي للمشروع يفرّق بوضوح بين "عميق/بسيط/غير منفَّذ" بدل التسويق المبالغ فيه — هذا يسهّل تقييم الاستثمار بدقة.
2. **تكامل واتساب حقيقي وليس Mock** — وهذه ميزة تفاضلية قوية في سوق يعتمد فيه كثير من العيادات على واتساب أصلًا للتواصل مع المرضى.
3. **معمارية Serverless منخفضة التكلفة التشغيلية** مقارنة بحل تقليدي يحتاج خوادم دائمة.
4. **عزل بيانات صارم بين العيادات (Multi-Tenancy)** مبني من الأساس وليس مُضافًا لاحقًا.
5. **تغطية اختبار حقيقية (42 اختبارًا) ضد بنية تحتية فعلية**، وليست اختبارات سطحية.
6. **نموذج فوترة اشتراك جاهز تقنيًا (Stripe)** — يحتاج فقط قرار تسعير واستراتيجية تسويق.

## 10. الفجوات والمخاطر قبل التوسّع (الجزء الأهم لهذا الاجتماع)

| # | الفجوة | التأثير على قرار التوسّع |
|---|---|---|
| 1 | **لا توجد استراتيجية تسعير مكتملة** (الفرق الفعلي بين Starter/Professional/Enterprise غير معرّف من حيث الحدود والميزات) | يجب حسمها قبل أي حملة تسويقية أو مبيعات |
| 2 | **لا مراجعة أمنية خارجية بعد** | مخاطرة قانونية وسمعية إذا تم التعامل مع بيانات مرضى حقيقية دون مراجعة مستقلة |
| 3 | **لا تشفير عند التخزين (Encryption at Rest) مفعّل بعد** | حاجز أمام أي عميل يشترط معايير امتثال (تأمين، مستشفيات كبرى) |
| 4 | **لا سياسة نسخ احتياطي/استجابة للحوادث موثّقة** | ضروري قبل توقيع أي عقد SLA مع عيادات حقيقية |
| 5 | **حدود Vercel Hobby تفرض تذكيرات يومية فقط (وليست لحظية)** | قد يقلل من جودة تجربة المستخدم مع نمو عدد العيادات؛ يتطلب ترقية للخطة المدفوعة |
| 6 | **إدارة الأسرار بدائية (متغيرات بيئة/عمود قاعدة بيانات)** | يجب معالجتها قبل تعدد العملاء بمقياس أكبر |
| 7 | **ميزات غير منفَّذة (توقيع إلكتروني، شهادات طبية، Push Notifications)** | قد تكون شرطًا لبعض العملاء المستهدفين — يجب تحديد الأولوية بناءً على السوق المستهدف |
| 8 | **بناء Docker غير مُختبر فعليًا بتشغيل حقيقي** | مخاطرة لمن يريد التوسع عبر الاستضافة الذاتية بدل Vercel |
| 9 | **لا بيانات سوق/عملاء حقيقيين بعد (المنتج لم يُختبر مع عيادة حقيقية خارج البيئة التجريبية)** | التوسّع قبل التحقق من ملاءمة المنتج للسوق (Product-Market Fit) قد يكون سابقًا لأوانه |

## 11. أسئلة مفتوحة للنقاش مع المستشار الاستراتيجي

1. هل الأولوية الآن هي **تحسين الجاهزية والامتثال** (أمن، تشفير، سياسات) أم **التوسّع التسويقي/المبيعات** بالمنتج كما هو؟
2. ما السوق المستهدف الأول للتوسّع؟ (محليًا/إقليميًا) وهل يفرض متطلبات امتثال معينة (HIPAA لو أمريكا، أو معايير محلية أخرى)؟
3. هل نحتاج تجربة تجريبية (Pilot) مع عيادة حقيقية واحدة قبل أي استثمار تسويقي أكبر؟
4. ما هو التسعير المناسب لكل خطة (Starter/Professional/Enterprise)، وما الفرق الوظيفي الذي يبرر الفرق السعري؟
5. هل نستثمر أولًا في إغلاق الفجوات الأمنية/الامتثالية، أم في الميزات غير المنفَّذة (توقيع إلكتروني، إشعارات Push)؟
6. هل البنية الحالية (Vercel + بدون طابور خلفي) قادرة على التوسّع لعدد كبير من العيادات مستقبلًا، أم نحتاج تخطيطًا لمعمارية بديلة لاحقًا؟
7. هل نحتاج فريقًا إضافيًا (أمن، مبيعات، دعم فني) قبل استقبال عملاء حقيقيين بشكل واسع؟

## 12. خلاصة وتوصية أولية

المشروع في حالة **جيدة تقنيًا وصادقة في توثيقها** — الأساس (المصادقة، عزل البيانات، المواعيد، الفوترة، واتساب) مبني بعمق حقيقي ومختبر فعليًا. لكن **الجاهزية للتوسّع التجاري ليست جاهزية تقنية بحتة** — الفجوات الحقيقية اليوم هي:
- استراتيجية تسعير وسوق واضحة
- إغلاق الفجوات الأمنية/الامتثالية قبل التعامل مع بيانات مرضى حقيقيين على نطاق واسع
- التحقق من ملاءمة السوق (Pilot حقيقي) قبل الاستثمار في نمو واسع

**التوصية:** مناقشة هذه النقاط مع المستشار الاستراتيجي **قبل** إضافة أي ميزات جديدة أو الدخول في حملة توسّع، والتركيز أولًا على: (أ) تجربة تجريبية مع عيادة حقيقية، (ب) خطة تسعير مبدئية، (ج) خارطة طريق لإغلاق الفجوات الأمنية الأساسية (تشفير + مراجعة أمنية + سياسة نسخ احتياطي).
